# ADR-004: 테스트 설명을 필수화

## 상태

수락됨

## 맥락

이 프로젝트는 TDD와 Harness 흐름을 전제로 한다. 테스트가 실패·통과의 신호뿐 아니라 **무엇을 검증하는 설계 문서** 역할을 해야 한다. 메서드명만으로 의도가 드러나지 않으면 Red-Green 사이클에서 회귀 원인 파악이 느려진다.

## 결정

- 새 테스트 또는 수정된 테스트는 **`@DisplayName`** 또는 **명확한 테스트 메서드명**으로 검증 목적을 설명한다.
- Given / When / Then 흐름이 코드에서 읽히게 작성한다.

## 검토한 대안

- 메서드명만 사용 (`shouldReturn400WhenUrlInvalid` 등)
- `@DisplayName`만 사용
- 테스트 클래스 주석으로만 설명

## 결과

### 장점

- 실패 로그와 IDE에서 검증 의도를 바로 이해할 수 있다.
- TDD Guard·CI 리포트에서 어떤 규칙이 깨졌는지 파악하기 쉽다.
- 주니어·리뷰어가 테스트를 읽는 진입 장벽이 낮아진다.

### 단점

- 테스트 작성 시 짧은 문서화 비용이 추가된다.
- DisplayName과 메서드명이 어긋나면 혼란이 생길 수 있다.

## 구현 시 유의사항

- AGENTS.md: 실패 케이스(URL 오류, API 키 누락, 외부 API 실패)도 동일 규칙을 적용한다.
- DisplayName은 한국어·영어 모두 가능하나, **검증 대상·기대 결과**가 포함되어야 한다.
- 참고 스타일: [movie 프로젝트 테스트](https://github.com/net1506/movie.git)
